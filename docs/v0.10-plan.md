# v0.10.0 plan

## The thesis

The five studies before this one measured the plugin against benchmark
instruments. This one is different: qon-ng is a real product — a sealed
STM32C071GBU6N humidity probe with no SWD header and no BOOT0 pin — taken from
an empty repository to firmware running on hardware, with the plugin as the
primary working aid throughout. Its `CLAUDE.md` instructs every session to use
the skills, the agents and the reference tools by default.

The verdict on what the plugin is built for is good, and the failures are
specific. Lookup-then-write against a version-exact index works. What defeats it
is a question the index cannot answer, in one of four shapes:

| Shape | What happened |
|---|---|
| The index is correct but the question is not a Zephyr question | Reaching the ROM bootloader. No tool here answers what a part does with a forced `PROGEMPTY`. |
| The index is authoritative **and wrong** | Two upstream defects in the pinned v4.4.2 — `fdc2x1x.c:41` treats a gain field index as a bit shift, `modbus_server.c:364` loops forever on register `0xFFFF`. |
| The answer is in the **composition** of files, not in any file | The SoC `.dtsi` selects `STM32_SRC_HSE` for the USB kernel clock; the board fits no crystal; the overlay overrode `status` and `pinctrl` and never `clocks`. |
| The question is what being wrong **costs** | An image that boots but does not enumerate is unrecoverable on that board. |

**Only the third shape generalises into plugin work, and it does so twice.** The
rest are properties of one product, and the discipline of this release is
refusing them — see *What did not generalise*.

The third shape produced a bricked unit. The chain is deterministic:
`clock_control_configure()` answers `-ENOTSUP`, `udc_stm32` returns `-EIO`,
`usbd_enable()` is never reached, the D+ pull-up is never asserted. The host sees
no device at all — not a failed enumeration, an absence. The build succeeds,
`.config` is clean, the linked image is clean. USB was that board's only reflash
path.

**0.10.0 closes the gap that produced it, and refuses the rest.**

## What the study settled

**The STM32 reference stopped above the mechanism that matters.**
`references/stm32.md` documented the bus-clock cell of a `clocks` property and
nothing further. Measured against the pinned tree rather than against the
project: 105 SoC `.dtsi` files across 26 families use `STM32_SRC_*` selectors,
and 173 board files override a domain clock. That is a gap in the middle of the
subject, not at its edge, and it stands independently of what qon-ng hit.

**A failure class exists that no gate in the plugin could see.** A phandle to a
disabled provider is legal devicetree. It is absent from `.config`, absent from
the linked image, and the build succeeds. The one thing that does record it is
the merged devicetree, which is the build's own output and which no tool here
read.

**A dev board is not a proxy unless the differences are enumerated.** The project
built a Nucleo bring-up target to catch exactly this class. The Nucleo fits a
48 MHz crystal, so the same SoC-default property resolved to a live clock and USB
came up. A green bench run would have authorised the image that bricked the unit.
This is real, but it is a project practice rather than plugin work — the plugin's
contribution is making the underlying property checkable, which `check_devicetree`
does.

**`check_environment` measured the wrong environment.** It reads
`ZEPHYR_SDK_INSTALL_DIR`, the CMake package registry and `python3` from the MCP
server's own process. The server is spawned once per session from the login
shell, so it never sees a `source env.sh`. Against a project that pins its own
SDK, interpreter and west — deliberately unregistered, so other workspaces on the
machine keep theirs — it reported a broken machine. Both `CLAUDE.md` and
`README.md` in that project carry a standing instruction to ignore the tool.

That is the same error the repository already refuses elsewhere: reporting
absence of evidence as evidence of absence, as with `CONFIG_` symbols outside the
catalogue. A tool a user is told to disregard is worse than no tool, because the
instruction generalises to the next finding.

## MCP tools

### T1 — `check_devicetree` reads the tree the build produced

`check_config` scans a devicetree fragment for `compatible` and nothing else,
because deciding anything about a property in an overlay needs to know which node
owns it and therefore which binding applies. A **merged** tree is a different
input: `build/zephyr/zephyr.dts` is complete, every label is declared in it, and
every `status` is resolved. A real parse is honest there.

Two checks.

**Generic.** Any enabled node whose `clocks`, `dmas`, `resets`, `power-domains`,
`io-channels`, `pwms`, `mboxes`, `iommus`, `nvmem-cells`, `phys`, `*-gpios` or
`*-supply` names a node that is not enabled. Deliberately a property list rather
than every phandle: `pinctrl-N` names pin configuration nodes, which carry no
status, and reporting those would produce findings the tree cannot support.

**STM32 domain clocks.** The generic check cannot see the case that mattered. In
`clocks = <&rcc 0x6 0x10c0058>` the phandle names `rcc`, which is enabled; the
disabled clock is reached through the numeric selector `0x6`, which is
`STM32_SRC_HSE`.

Nothing about the selector table is restated in this repository. The `soc` node
names the part and the series (`"st,stm32c071", "st,stm32c0"`), the part's own
`.dtsi` names the clock header through its include chain, and the header is
evaluated for both the `STM32_SRC_*` values and the
`STM32_PERIPH_BUS_MIN`/`MAX` range that separates a bus entry from a source
selector. The selectors are chained increments upstream —
`STM32_SRC_HSI48 (STM32_SRC_HSI + 1)` — so a copied table names the wrong clock
the moment one is inserted.

Selector to node is derived, not tabulated, because the families disagree: a
selector names a source and one of its outputs, so trailing segments are dropped
until a label matches. `STM32_SRC_PLL2_Q` finds `pll2`, `STM32_SRC_PLL1_Q` finds
`pll` on H7 and `pll1` on U5, `STM32_SRC_PLLSAI2_POST_R` needs two drops, and
`STM32_SRC_HSI_KER` resolves to `clk_hsi`, which is the clock it is taken from
and the node that can be off.

Three populations, as everywhere else here. Where the family header cannot be
read, or a selector matches no node, the finding is *not judged* and names what
was not established.

### T2 — `check_environment` scopes its claims to what it can see

It detects a project-local toolchain — an activation script, a project `.venv`, a
project `zephyr-sdk-*` — bounded by the workspace or repository root, and never
adopting the home directory. When those markers are present and none is active in
this process, the Python, west and SDK findings become observations that name the
activation which has not run, instead of blocking problems.

`ok` is false in that case rather than true. Not established is not the same as
clean, and reporting `ok` for a check that could not run is the failure this tool
was committing in the first place. With no such layout, a missing SDK is still a
blocking problem and still carries its install command.

## Skills

### S1 — Domain clocks and crystal-less boards, in `zephyr-platforms`

`references/stm32.md` gains the two-entry `clocks` form and what each entry does,
the failure chain a wrong selector produces, and the rule that enabling a node
adopts every property it inherits — so the resolved value is read in
`build/zephyr/zephyr.dts`, not in the overlay that was written. Selector values
are looked up with `get_source` for the family in hand and never restated.

Crystal-less boards get their own section: what changes when `clk_hse` and
`clk_lse` are disabled, that every domain clock must then select an internal
source, and that USB full speed is legal only with HSI48 trimmed by the CRS,
because a free-running HSI48 does not meet the ±0.25 % the specification
requires.

### S2 — Boot mode and the ROM bootloader, in `zephyr-platforms`

`references/stm32-boot-and-recovery.md` is new. Before it, the reference
mentioned `BOOT0` once, in a debugging aside, with no explanation of what boot
mode selection is — while USB DFU without a probe is how a large share of cheap
STM32 boards are programmed.

It covers what selects the boot area (`BOOT0`, `nBOOT_SEL`, `nBOOT0`,
`BOOT_LOCK`, RDP) and that the applicable terms are a property of the part rather
than a general rule; the system-memory bootloader and its `0483:df11` DFU
interface; that a jump from application code into system memory does not work on
the families implementing an empty check; the option-byte write window that can
leave a part unreachable; and the three IWDG properties that drive design
decisions, including that `CONFIG_WDT_DISABLE_AT_BOOT` is invisible unless the
driver selects `HAS_WDT_DISABLE_AT_BOOT` and is otherwise dropped without a
message.

It closes with the lookup to make when the Zephyr lookup does not settle it: the
CMSIS device header, which `get_source` reads at the manifest's pinned revision,
so a register offset is read rather than recalled.

## Shipped reference

### R1 — ST's AN2606 and AN3156 ship with the plugin

Under `plugin/reference/st/`, so a citation to a document and section is
checkable from an installed copy rather than against a URL that moves. They are
ST copyright, redistributed unmodified, and outside the Apache-2.0 grant that
covers the rest of the plugin; `reference/st/NOTICE.md` states that and names the
revisions, because AN3156 first listed the STM32C0 series at Rev 16 and an
earlier revision's statements cover those parts only by exclusion.

They sit outside `plugin/skills/` deliberately. `scripts/quality/skills.mjs`
applies the catalogue-backed checks to every Markdown file a skill owns, and
those checks exist to stop *the plugin's own claims* escaping verification by
being moved into `references/`. A verbatim third-party document is not a plugin
claim.

AN2606 is 13,625 lines organised one section per device family, so S2 names the
section path to read for a given part. It is a lookup, never a read-through.

## What did not generalise

Each of these was proposed from the study and refused. They are recorded so the
next cycle does not re-propose them.

| Proposal | Why it was refused |
|---|---|
| Recovery as a `zephyr-architect` section | Downstream of "this board has no SWD and no BOOT0". Most targets have a debug port, where a wrong image costs a reflash. |
| A cycle-**risk** axis in `zephyr-hardware-iteration` | Same precondition. The skill measures cycles per hour, which is the right axis for a board that can be reflashed. |
| Overriding Zephyr's fatal handler | The weak default halting forever is correct with a debugger attached, which is why it is the default. The retry-count design is one product's. |
| Source-is-evidence-not-oracle | Two upstream defects in one tree is an anecdote. As guidance it would fire constantly and produce noise. |
| Raw-flash storage rules | One project's persistence design. Zephyr users mostly use NVS, ZMS or settings, which own the erase-unit and blank-slot problems. |
| Mutation checking, a findings register, an evidence vocabulary | Process and posture, not Zephyr procedure. The second is the governance theatre AGENTS.md refuses. |
| A `set()`-versus-`list(PREPEND)` hook check | Guards a magic-prepend pattern the plugin already steers away from by teaching board `.conf` files. |

The general form: **a lesson from one product is not plugin material because it
can be phrased universally.** It is plugin material when it produces a lookup, a
command or a check, and when a project on different silicon with a debug port
would hit it.

## Method

### M1 — A check must be shown to work in both directions

`check_devicetree` is verified against a real Zephyr-generated merged tree, not
only against a fixture. `nucleo_h743zi` — an H7, a different family from the C0
that produced the defect, so the header resolution is exercised twice:

| Tree | Result |
|---|---|
| Stock | 0 problems, 48 references reaching enabled nodes, 1 not judged (`STM32_SRC_TIMPCLK1`, which has no node) |
| One clock node disabled | exactly 1 problem, naming `fdcan1`, `STM32_SRC_PLL2_Q` and `pll2` |

Zero findings on a working upstream board is the necessary condition. A checker
that reports on a healthy tree is one people learn to skip, which is the same
failure `check_environment` was committing.

Two defects surfaced from the tests rather than from reading, both in the new
`check_environment` detection:

- the project walk escaped the repository and claimed a stray `~/zephyr-sdk-*` as
  the project's toolchain, which would have silenced the finding the tool exists
  to make;
- the test that caught it then passed only on a machine with no registered SDK.
  It now runs against an empty `HOME`, so it measures the product rather than the
  developer's machine — the rule in AGENTS.md, applied to a test that had just
  broken it.
