# v0.9.0 plan

## The thesis

Four studies have now measured this plugin. Every measurement of what it
**returns** is good. Instrument 0 passes 35 of 37 capability checks. Where a tool
was called in the gateway build, its answer was correct and often decisive — one
`get_kconfig` call, made before a line of configuration existed, prevented the
exact defect that defined 0.8.0 from ever occurring. On the fact benchmark the
plugin arms have led or tied in every study.

Every measurement of whether it is **reached for** is poor, and has been for four
releases:

| | ESP32 0.1.1 | L475 0.2.0 | N6 health 0.7.0 | N6 gateway 0.8.0 |
|---|---:|---:|---:|---:|
| MCP share of tool calls | 10.3% | 6.0% | 2.2% | 4.4% |
| skills fired | 1 of 15 | — | — | **1 of 17** |
| agents fired | 0 of 4 | 0 | 0 | **0 of 5** |

0.8.0 wrote a `hardware-bringup` agent and a `zephyr-hardware-iteration` skill
for exactly the work the gateway session did. Both are good. Neither fired. At
call 95 the session rediscovered, by shell experiment, the skill's own opening
rule — that an alternate load path may already exist — and built `tools/reflash.sh`
around it while the skill sat unread.

So the question for 0.9.0 is not what else to write. It is **which channels
actually reach a working session**, and the gateway study answers it precisely.
Three things landed, and all three share a shape:

1. **The SessionStart message.** Read at call 0, acted on at call 7.
2. **A field in a tool answer.** `"hasPrompt": false, "selectedBy": []` changed
   what the session wrote, without any prose telling it to care.
3. **The PreToolUse write nudge.** Its tool advice was taken. Its agent referral,
   in the same sentence, was not.

Each is **information embedded in something the session was already going to
read**. Nothing that required the session to go and fetch guidance was fetched.

**0.9.0 moves guidance into the answer, and stops relying on referral.**

## What the gateway study settled

**The index models the wrong layer for the question that matters most.** The
study's central question was whether an I²C part at 0x68 reporting `WHO_AM_I =
0x19` is supported. The session answered it correctly in three steps: read the
register off the hardware, grep the driver headers for which identity constants
are accepted, correct its earlier conclusion. The authoritative fact is
`MPU6880_CHIP_ID 0x19` in `drivers/sensor/tdk/mpu6050/mpu6050.h`, and **the index
does not model driver identity constants at all**.

0.8.0's instantiation corpus — the flagship feature, built for this class of
error — was called after the question was settled, and would have answered it only
by inference: `usedIn.boards: [m5stack_atoms3, m5stack_fire, m5stickc_plus]`
requires the reader to already know what an M5Stack board carries. The corpus
stores the node names those devicetrees use — `mpu6886@68`, which names the part
outright — and does not render them.

**`get_board` and `check_config` were loaded and never called.** Seven of sixteen
tools went unused for 67 minutes after being fetched. Those two carry more 0.8.0
work than any other pair: per-target overlay filenames, Twister-metadata
labelling, SoC-identity board links, the alternate load path, the entire
promptless verdict path. This is not discovery failure. They were in the tool
list.

**Two real defects in instrument 0**, both narrow and both about honesty rather
than capability. `check_config` returns `ok` for a symbol the index elsewhere says
it cannot judge, and `search_bindings` will not match part of a compatible while
volunteering a reason to stop looking.

**One false positive in a hook.** `check-build-failure` classifies on the content
of Bash output rather than on whether a build ran, and fires on any command that
prints a build log.

**The fact benchmark went to the web arm, 36 to 35 to 35**, and the single point
of separation was an aggregate question the index cannot answer. Asked how much
upstream material names this board, both plugin arms answered *two suites, both
through `platform_allow`* and explained the mechanism better than the answer key
did. The web arm answered *ten — one sample and nine tests*, and was right: eight
of them carry a `boards/` file named for the board or one of its qualified
targets and never appear in a Twister key.

The most useful of those eight is
`tests/drivers/spi/spi_loopback/boards/nucleo_n657x0_q_stm32n657xx_sb.overlay`,
which is ST's own SPI loopback configuration for this exact target, complete with
the DMA channels and request numbers and `CONFIG_NOCACHE_MEMORY=y`. The gateway
session wrote its own from scratch and ran at 1 MHz without DMA. Nothing it built
was wrong; it never learned the answer was already published.

The six file-level control questions separated nobody — eighteen answers, every
one full marks. That is the third study in which a web arm resolving the release
tag and reading `raw.githubusercontent.com` file by file reaches parity on
file-level questions. **Version anchoring has stopped being a differentiator, and
the plugin should stop being sold on it.** What remains is speed — the plugin arms
finished in two-thirds of the wall clock — and aggregates over corpora the index
actually holds.

## Index and corpus

### I1 — Model what a driver will accept, not only where it is used

**The highest-value item in this release.** For every driver that gates
initialisation on an identity register, record the contract:

| field | example |
|---|---|
| compatible | `invensense,mpu6050` |
| driver source | `drivers/sensor/tdk/mpu6050/mpu6050.c` |
| identity register | `0x75` (`MPU6050_REG_CHIP_ID`) |
| accepted values | `0x68` `MPU6050_CHIP_ID`, `0x70` `MPU6500_CHIP_ID`, `0x71` `MPU9250_CHIP_ID`, `0x19` `MPU6880_CHIP_ID` |

Extract by locating each driver's `DT_DRV_COMPAT`, then the `*_CHIP_ID`,
`*_DEVICE_ID`, `*_WHO_AM_I` and `*_ID_VAL` defines in the driver's own header,
and the comparison against them in the init path. Where the pattern cannot be
recognised, store nothing — an absent record must never read as "accepts
nothing".

This makes both directions answerable:

- *forward*: "will `invensense,mpu6050` take my part?" → the accepted set.
- *reverse*: "what accepts `0x19` at register `0x75`?" → the compatible.

The reverse direction is the one a developer at a bench actually has, and no
existing tool can answer it.

### I2 — Render the node name in the instantiation corpus

The corpus already stores which devicetree files name a compatible. It renders the
board list. **The node name is the part number**, and it is what turns

> used in `m5stack_atoms3`, `m5stack_fire`, `m5stickc_plus`

into

> used in `m5stack_atoms3` as `mpu6886@68`, `m5stack_fire` as `mpu6886@68`,
> `m5stickc_plus` as `mpu6886@68`

The second answers the question. The first requires the reader to know the
hardware already. Same data, one join away.

### I3 — Make `search_bindings` match part of a compatible

`st,stm32-digi-temp` resolves. `stm32-digi-temp` and `digi-temp` both return *no
bindings matched*, and the miss volunteers "Remember that out-of-tree drivers are
not in this index" — a reason to stop looking, offered about a binding that is
present. Searching bindings is the tool for when the compatible is precisely what
is not known; recall on a fragment is the whole point.

Add substring matching on the compatible, and suppress the out-of-tree hint when a
substring search would have hit.

### I4 — Index the board-named files inside `samples/` and `tests/`

The sample and test corpus records Twister metadata — `platform_allow`,
`integration_platforms`, `depends_on`, scenario names. It does not record that a
suite ships `boards/<board>.overlay` or `boards/<qualified_target>.conf`.

Those files are the most directly useful upstream material a board has: they are
how the vendor configures each peripheral on that exact target, including the
parts nobody would guess. On this board they cover ADC, CAN, DMA, I²C, SPI, UART
and I²S across eight suites, and the plugin can see none of them.

This is the same shape as the defect 0.3.0 fixed. There, `get_sample` rendered
`integration_platforms` and not `platform_allow`, and both plugin arms concluded
no upstream Wi-Fi sample named a board when seven did. Here the corpus records
Twister keys and not filenames, and both plugin arms undercounted by eight.

Add board-named files under `samples/` and `tests/` to the corpus, keyed by the
qualified target their filename resolves to, and render them in `search_samples`
and `get_board`. `get_board` is the natural home: *upstream configures this
peripheral on this target here.*

The same gap covers the compatible-usage corpus from 0.8.0, which reports
`boards/`, `dts/` and shields but not `samples/` or `tests/`. P₀ diagnosed that
itself, unprompted, mid-answer.

### I5 — Never return `ok` for a line that was not judged

`index_status` says, of this index's module coverage:

> Module sources are readable at their manifest revisions, but no module Kconfig
> or bindings were evaluated, so a symbol a module redeclares is not judged.

`check_config` returns `CONFIG_LV_USE_MONKEY=y` as `ok, bool` — the identical
verdict `CONFIG_GPIO=y` receives, which *was* verified in full. Suppressing the
promptless complaint for those symbols is correct; reporting the result as `ok` is
not. The check verified nothing about that line and says it did.

Add the third verdict — *not judged*, with the reason — and count it separately in
the summary line.

## MCP tools

### T1 — `get_binding` carries the identity contract

From I1, inline in the answer for any compatible that has one. This is the
release's clearest instance of the thesis: the fact that decides the question
arrives in the answer the session was already reading, with no skill to invoke and
no agent to delegate to.

### T2 — `search_bindings` answers the reverse lookup

Accept an identity value and, optionally, a register: *which compatible accepts
`0x19`?* Also carries I3's substring fix.

### T3 — `check_config` reports three populations

From I5.

### T4 — `get_board` renders upstream's own configuration for the target

From I4. Where a sample or test ships a `boards/` file that resolves to one of
this board's qualified targets, say so and name it. A developer bringing up SPI
on this board should be told that ST publishes a loopback overlay for it before
they write one.

### T5 — `get_board` renders the memory budget, not only the metadata

0.8.0 labels the Twister figures and points at the devicetree partitions. Go one
step further and state the number: this board's application budget is **511 KB at
`0x34180400` from `axisram2`**, and four further 448 KB banks exist and ship
disabled. A developer sizing an image should not have to derive it.

### T6 — Name the tools in the no-index and SessionStart paths

The MCP tools are deferred: they are absent from the model's tool list until
fetched by name. A session that never fetches them cannot call them, and nothing
in any answer says they exist. The SessionStart message and the no-index message
should both name the exact fetch, once, in the form that works.

## Hooks

### H1 — `check-build-failure` must gate on the command

It classifies on the content of Bash output. It fired on an observer command that
merely *printed* captured compiler errors, and returned the full "The Zephyr build
failed" advice including a referral to `build-triage`. Any `cat build.log`, any
grep over CI output, any diff of two build logs qualifies.

Gate on the command being a build — `west build`, `west twister`, `ninja`,
`cmake --build`, `make` — and require a non-zero exit. Output content then selects
the class, as it does now.

### H2 — The write nudge names the identity question

The PreToolUse hook on a devicetree write already says to check every compatible
with `get_binding`. Add the sentence that matters for a sensor node: **confirm the
driver's identity check accepts the part you actually have**, and that binding a
driver whose check the part fails produces a device that initialises and returns
numbers that are not readings.

### H3 — Drop the agent referral from the write nudge

Three studies, zero agent invocations, and in this one the same sentence's tool
advice was taken while its agent referral was not. The referral is costing
sentence length in the one channel that demonstrably reaches. Spend the words on
H2 instead. See A1.

### H4 — Keep SessionStart exactly as it is

It works. It spoke in a docs-only project, named `ZEPHYR_AI_INDEX` and why
`ZEPHYR_AI_PROJECT_ROOT` does not work, and the session invoked `zephyr-index` one
call later. Both 0.8.0 changes to it landed. Add only T6's tool-fetch sentence.

## Skills

The gateway session's `LESSONS.md` is the richest source any study has produced.
Each item below is general — none mentions this board, and most do not mention
STM32. The routing rule is the project's standing one: behaviour that generalises
becomes a skill, and it goes in the skill a session would already have open.

### S1 — Driver identity, in `zephyr-drivers-sensors`

Two rules, and the second matters more:

- **Check the driver's actual identity test before declaring a part
  unsupported.** A part whose marketing name appears nowhere may still be
  accepted; the authoritative fact is a constant in the driver's header.
- **Never bind a driver whose identity check the part would fail.** It will
  initialise, or half-initialise, and produce numbers that look like readings. A
  device that is absent is better than a device that lies.

Neither appears in any 0.8.0 skill or agent. `WHO_AM_I` and `CHIP_ID` appear
nowhere in the plugin.

### S2 — Absence is a checkable fact, in `zephyr-drivers-sensors`

"This RTOS has no driver for X" is worth stating only with the search behind it:
the string appears nowhere in the tree; here are the drivers that do exist for
that class; here is the protocol each speaks; here is why none matches. That
paragraph is what justifies writing your own driver, and it is what stops the next
person re-deriving it. The gateway session produced exactly this for the FPC1020A,
naming `adh-tech,gt5x`, `zhiantec,zfm-x0` and `hzgrow,r502a` and the framing each
uses.

Add the corollary: **look for the subsystem before writing an application-level
driver.** Discovering that `drivers/biometrics/` exists changes the shape of the
solution even when the answer is still to write your own.

### S3 — Error contracts, in `zephyr-debugging`

**`-EALREADY` is success.** Bringing up an interface that auto-started returns it,
and treating every non-zero return as failure produced a confident, prominent,
entirely false "ethernet FAILED" while the link was working. Read the documented
return set; idempotent operations have an "already done" code and it is not an
error.

**Distinguish "not yet" from "never".** A subsystem that will be ready in one
second and one that never will deserve different words and different consequences.
Wait, bounded, for the steady state before reporting it.

`EALREADY` appears in no skill and no agent today.

### S4 — Foreign callbacks, in `zephyr-rtos-patterns`

**Do nothing in a callback you do not own except hand the work to a context you
do.** Callbacks run on stacks sized for the subsystem that owns them. With
immediate-mode logging there is no log thread to absorb formatting, so a single
log line inside a network-management callback can overflow a stack that someone
else sized — and did, 2.5 seconds into every boot.

### S5 — Measure stacks, in `zephyr-rtos-patterns`

**Do not estimate stacks; read the high-water marks under load.** With stack
initialisation enabled the shell reports true per-thread usage, which turns stack
sizing from superstition into a table. Do it while the system is doing real work.
And note that some driver threads have sizes fixed in their source and cannot be
configured — worth recording where the next person will see it rather than
treating as a crisis.

### S6 — Protocol decoding, in `zephyr-debugging`

The gateway's worst bug, and it is entirely general: **a field whose meaning
depends on the outcome cannot be decoded unconditionally.** A 1:N search reply
carried a privilege level on success and a status code on failure, in the same
byte. A status table correct for every other command in the protocol turned
privilege 1 into failure code 1, and a valid credential was refused.

- Decide the outcome from a field that is unambiguous, then interpret the
  overloaded one.
- A shared enumeration feels safe because it is usually right. Ask which commands
  it actually applies to.
- **When a decode bug fails closed it blames the hardware or the human.** Suspect
  your own decoder first — especially when the device answered promptly and with a
  valid checksum, which means it understood the question.

### S7 — Evidence discipline, in `zephyr-hardware-iteration`

The single highest-leverage habit in the study, and the skill's "Characterise
precisely" section is where it belongs:

- **An identification that cannot be falsified is not an identification.** Report
  the value you read next to the conclusion you drew from it.
- **Prefer a handshake with a checksum over an acknowledgement.** A bare ACK
  proves only that something is at that address. A response whose CRC validates
  cannot have come from a device that did not send it.
- **When a read returns zeros, read something known-non-zero through the same
  path.** Zeros are ambiguous — blank storage, a failed read reporting success, a
  peripheral in the wrong security state. If the control read is also zero, say
  that, rather than choosing the flattering interpretation. "The fuse is blank"
  and "nothing is coming back from this path" are different claims.
- **A response that changes with state tells you what it means.** Perturb the
  system deliberately and watch which bytes move.
- **Report raw bytes on the failure path.** "Not recognised" locates nothing;
  "id 2, code 0x01" locates everything.

### S8 — Firmware that explains itself, in `zephyr-hardware-iteration`

The skill has "Report degradation on the device". Extend it with the structure
that made it cheap:

- **Build the health registry before the features.** One place where every
  subsystem records state and a one-line detail, feeding the boot banner, the
  shell, the network registers and the indicator LED. Written once, early, it
  costs nothing per feature; retrofitted, it produces N inconsistent answers.
- **Latch faults, not weather.** An unplugged cable is not a device defect. A
  fault indicator that latches on transient external conditions is one operators
  learn to ignore.
- **Report on change, not on schedule.**
- **Prove the safety mechanism by firing it.** "The watchdog is armed" is a claim
  about configuration. A command that hangs the system deliberately, and a known
  external signature for the reset, is a claim about reality.

### S9 — Working with a human at the bench, in `zephyr-hardware-iteration`

New, general, and absent from the plugin:

- **Batch the human's physical actions and state the rhythm first.** Someone at
  the bench cannot see your terminal. Press, hold, lift, repeat — with a
  synchronisation point that means go.
- **Make interactive timeouts generous.** Fifteen seconds to present a finger, not
  eight. Timing out halfway through a three-step enrolment costs a restart with a
  person waiting.
- **One owner per serial port.** Two readers silently steal each other's bytes and
  produce an error that blames the hardware.
- **The person at the bench is the authority on physical facts** — which LED is
  lit, what is plugged in. Ask, and believe the answer over the schematic.

## Agents

### A1 — Decide what agents are for, or stop shipping them

Zero agent invocations across four studies. The gateway study removes the last
comfortable explanation:

- The nudges land. The same PreToolUse sentence whose tool advice was followed
  named `devicetree-specialist`, and it was not.
- The wording is not too broad. `build-triage` was narrowed in 0.8.0 specifically
  so it would stop claiming easy failures.
- The agent is not missing. `hardware-bringup` was written for this workload and
  its description matches what happened almost line by line.

The plausible remaining explanation is structural: in a bring-up session the state
is entangled, the caller needs the details, and delegation costs more than it
saves. If that is right, the content in the agents belongs in skills and in tool
answers, and shipping five agents that never run is a maintenance cost with no
measured benefit.

**This is a measurement task before it is a design task.** Run a session where the
observer *instructs* the use of `hardware-bringup` on a real bring-up problem and
compare the result with the unaided session. That separates "never invoked because
it would not help" from "never invoked because nothing invokes it". Until that
runs, do not write another agent.

## Method

### M1 — Hook output is now in the transcript

Session transcripts record `attachment` records of type `hook_success` carrying
the hook name and its stdout. The replay procedure the 0.7.0 study had to invent
is no longer needed for mechanism questions; replay remains the way to test
counterfactuals.

### M2 — Publish grounding acts, not tool-call share

Tool-call share understated the plugin's contribution by roughly eight times in
this study: 4.4% of calls, but about 35% of everything the session verified. One
`get_kconfig` carried 27 symbols. The plural-input design from 0.3.0 is what makes
the two diverge, and the ratio that gets quoted should be the one that measures
questions answered.
