# v0.8 plan

Written against the NUCLEO-N657X0-Q study (plugin 0.7.0). Findings live in
`stm32-n6-nucleo/PRE-RUN-FINDINGS.md` and `RESULTS-instrument-{0,1,2}.md` of the
evaluation repository.

## What instrument 1 settled, and what it changes here

Three arms, twelve questions, all valid: plugin+web **35/36**, plugin-only
**35/36**, web-only **33/36**.

**The plugin is self-sufficient.** Arm P₀ made **zero web calls with the open
internet available** — 71 MCP calls, 56 of them `get_source`. Third study, third
confirmation.

**The web arm is not a straw man, and two predictions died on that.** It anchored
itself to `refs/tags/v4.4.2` → `671f64aa…`, the annotated tag object for the exact
commit the plugin pins, and read the tree file by file from
`raw.githubusercontent.com`. On file-level questions that is parity by
construction. Treating "web access" as access to prose was the error; it is
access to the source tree, and it costs 96 fetches rather than being wrong.

**The single question the plugin won is the one that asks an aggregate.** Q10 —
what names this board, how many, through which Twister key — separated 35 from
33. Public web interfaces cannot answer it: GitHub code search needs auth,
grep.app rate-limits, the tree API truncates. An index answers it trivially.

That is the durable advantage, and it should shape this release: **corpus
questions, not file questions, are where the plugin is irreplaceable.** M1 and
T3 are the two workstreams that widen it; T6 and H1 protect against being wrong
where the web is merely slow.

**The catalogue gap cost nothing.** Both plugin arms hit the missing
`STM32N6_*` symbols, read the miss correctly as a limit of the catalogue rather
than as absence, recovered with `get_source`, and returned answers richer than
the answer key. **M2 is therefore a quality-of-life item, not a correctness
one**, and its priority drops accordingly; T2 is the better-value half of that
pair.

## Coverage rule

Every finding is routed to a surface, and every surface appears below:

| surface | workstreams |
|---|---|
| Hooks | H1–H4 |
| MCP server and index | M1–M4 |
| Tools | T1–T7 |
| Skills | S1–S9 |
| Agents | A1–A3 |

Defects map to code. Behaviour — what the agent tried, in what order, what it
discovered by trial and error — maps to skills and agents. A plan listing only
code changes discards the larger half of what the study measured.

**Skills and agents must be written as universal.** A lesson learned on an
STM32N6 about boot pins becomes guidance about boards whose debug port depends
on strap state. It does not become a page about JP2. The test for every skill
change below: would it help on a board nobody here has ever seen?

## Hooks

### H1 — the write validator gives a clean bill to a build-breaking file

**Highest priority in this plan.** `validate-zephyr-edit` reports *"checked 24
Kconfig assignments … no problems found"* on a `prj.conf` containing
`CONFIG_USE_STM32_HAL_DTS=y`, which Zephyr's `check_no_promptless_assign`
rejects outright.

The index holds the truth: `has_prompt=0`, declared at
`modules/Kconfig.stm32:186`. The finding is suppressed by a guard whose stated
reason is that "the real declaration lives in a module Kconfig that is only
present when that module is":

```sql
(SELECT COUNT(*) FROM kconfig_definition d WHERE d.symbol_id = k.id
  AND d.file LIKE 'modules/%') AS module_defs
```

`zephyr/modules/Kconfig.stm32` is Zephyr's own file, always present in the tree,
and fully indexed. It is not a module's Kconfig; it is upstream's hub of Kconfig
files *describing* modules. The path prefix `modules/` does not mean what the
guard assumes.

Measured on a project-scoped index, the guard silences the promptless check for
**745 symbols**, including **126 of the `USE_STM32_HAL_*` family** — exactly what
a developer reaches for when a HAL component is needed.

**Change.** Replace the path-prefix heuristic with the question it was trying to
ask: *is the declaring file inside the tree this index was built from?* A
definition the ingest read is a definition the catalogue can see, wherever it
sits. Reserve suppression for symbols whose declaration is genuinely absent —
the `type IS NULL` case already covers that.

**Regression fixture.** The existing fixture cannot catch this, for the same
reason 0.2.0's devicetree fixture could not catch its gate: it does not contain a
promptless symbol declared under `modules/`. Add `USE_STM32_HAL_*` to the corpus
and assert the finding fires.

### H2 — the build-failure hook does not recognise Zephyr's promptless error

The same mistake, missed a second time after the build. Zephyr emits, from
`scripts/kconfig/kconfig.py:150`:

```
{sym} is assigned in a configuration file, but is not directly
user-configurable (has no prompt). It gets its value indirectly from other
symbols.
```

No Kconfig pattern matches. `assigned to.*but has no prompt` is a different
phrasing and cannot cross the line break upstream places between "directly" and
"user-configurable"; `Kconfig[^\n]*\berror\b` requires `error` *after* `Kconfig`
on one line, and here it precedes it. The failure falls through to generic
advice while the correct advice sits unused in the same table.

**Change.** Match the real strings, with `s`-flag or newline-tolerant patterns.
Build the pattern set from a corpus of **actual Zephyr error output**, not from
paraphrase — collect one real failure per class (promptless, undefined symbol,
devicetree property, missing binding, board not found, region overflow, host
environment) and assert the routing for each. The corpus is the deliverable; the
regexes are downstream of it.

### H3 — "no problems found" claims more than the check knows

The acknowledgement added in 0.3.0 solved a real problem: silence was
indistinguishable from a check that never ran. It overshot. When the validator
skips a line because its view is incomplete, the summary still counts that line
as checked and then reports the file clean.

**Change.** Report three populations, not one: lines verified, lines outside the
catalogue, lines the check declined to judge and why. *"Checked 24 assignments —
21 verified, 3 outside the catalogue, no problems in what could be judged"* is
honest and just as reassuring. This is the same discipline `get_board` already
applies when it declines to render conditional runner arguments.

### H4 — SessionStart is silent in a first-day firmware project

`check-index.mjs` speaks only when the project root holds nothing but
dot-entries. A single `docs/` folder of board manuals silences it —
demonstrated by replay: an empty directory gets the full prompt, the same
directory plus `docs/BOARD.md` gets nothing.

The anti-nagging rule is sound; the predicate is too strict. A directory holding
only documentation is the *first day of a firmware project*, which is the case
the message was written for.

**Change.** Widen the predicate from "empty" to "holds nothing that identifies
it as another kind of project" — no `package.json`, `Cargo.toml`, `go.mod`,
`pyproject.toml`, `Makefile`, or source tree in a foreign language. Documentation,
`.git`, and editor state do not disqualify.

**Note for the record.** The cold start worked anyway: `index_status` refused to
answer without an index, named the `zephyr-index` skill, and a correct
project-scoped index existed four minutes in. Tool-level refusal is carrying the
weight SessionStart was meant to carry, and it works. H4 raises the floor; it is
not load-bearing.

## MCP server and index

### M1 — module sources are invisible, and on STM32 that is where the answers are

**34% of the session's grounding lookups (27 of 80) read
`modules/hal/stm32/stm32cube/**`** — CMSIS headers, HAL driver sources, register
definitions. The index covers the Zephyr tree only, so the plugin could not have
answered them at any activation rate.

This is not an STM32 quirk. The question "does this driver work on my silicon"
is answered in the vendor HAL for every vendor Zephyr supports.

**Change.** Extend `get_source` to read files from the workspace's module trees
as well as the Zephyr tree, resolved through the west manifest already recorded
in `westManifestHash`. Full semantic ingestion of HAL sources is out of scope —
file-level read at the pinned revision closes most of the gap, exactly as
`get_source` did for the Zephyr tree at 0.2.0.

Record module coverage in the coverage map so the answer can say what it did and
did not look at.

### M2 — per-SoC Kconfig is invisible in both catalogue and project indexes

`STM32N6_BOOT_SERIAL`, `STM32N6_RIF_OPEN`, and `STM32N6_NPU` are absent from the
shipped catalogue index **and** from the project-scoped index the session built.
They live in `soc/st/stm32/stm32n6x/Kconfig`, sourced only once an SoC is
selected. `SOC_STM32N657XX` is present, because `Kconfig.soc` is sourced
unconditionally.

`STM32N6_BOOT_SERIAL` is not incidental: it is the symbol every
`stm32cubeprogrammer` argument on this board is guarded on. `get_board` cites it
by name and `get_kconfig` cannot resolve it.

**Instrument 1 downgraded this from a correctness risk to a cost.** Both plugin
arms hit the miss, read it as a catalogue limit rather than as absence, recovered
by reading the Kconfig with `get_source`, and answered better than the key. The
hedge works. What remains is the extra round trips and the fact that `get_board`
cites a symbol `get_kconfig` cannot resolve. **Do T2 first; treat the ingest work
below as optional for this release and fold it into M4 if M4 lands.**

**Change, in two parts.**

1. **Ingest per-SoC Kconfig trees under a scope**, the way 0.5.0 gave sysbuild
   its own namespace. A symbol reachable only when `SOC_SERIES_X` is selected is
   still a fact about the tree; it needs a qualifier, not omission.
2. Until then, **make the miss informative** (see T2).

### M3 — the reproducibility hashes are stored and never surfaced

0.7.0 records `input_hash` beside `content_hash` and describes a two-machine
diagnosis built on the pair. `index_status` renders neither; it renders
`contextFingerprint`, which answers a different question. The procedure the
release describes cannot be carried out through any tool.

**Change.** Render both in `index_status`, labelled by what a difference in each
one means. One line each.

### M4 — the resolved build is the primary source and the index cannot read it

`coverage.resolvedBuild` is `incomplete` in every index built so far, and the
note is accurate: no resolved build output is ever ingested. Yet
`build/zephyr/zephyr.dts` and `build/zephyr/.config` are the only artefacts that
state what the build *actually* used — every question about a merged devicetree,
a resolved Kconfig value, or an applied overlay is answered there and nowhere
else.

The session read `build/zephyr` directly three times and read the generated
`.config` to confirm symbols had taken effect.

**Change.** Ingest a resolved build when one exists in the project, as an
additional scope layered over the catalogue. This subsumes M2 for any project
that has built once, because a resolved `.config` contains every SoC symbol the
catalogue cannot reach.

## Tools

### T1 — `get_board` links near-twins by name, and silicon confusion is not nominal

The confusable-boards feature works on the pair it was designed for
(`disco_l475_iot1` ↔ `b_l4s5i_iot01a`, "these share a marketing name and a SoC
series"). It does not link `nucleo_n657x0_q` and `stm32n6570_dk`, which share
the `stm32n657xx` SoC and differ on the external flash part, the `--extload`
file, the download address, the target count, and the declared RAM — every one a
thing that breaks a build.

**Change.** Add SoC identity as a second predicate alongside name similarity, and
label which relation fired. ST's naming makes same-silicon boards look unrelated
far more often than not.

### T2 — a context miss should name the context

`get_kconfig` answers `CONFIG_STM32N6_BOOT_SERIAL` with *"not found … no
sufficiently close spelling match"*. The hedge that follows is well-judged and
prevents a confident falsehood, which is why this is a quality issue rather than
a correctness one.

**Change.** When a miss matches an indexed SoC-series or board prefix, say so:
*"declared under SoC series `stm32n6x`, which this catalogue index does not
resolve; build a project index for a board on that series, or read
`soc/st/stm32/stm32n6x/Kconfig` with get_source."* A miss that names its own
remedy is worth several times one that does not.

### T3 — nothing answers "does this driver fit my silicon"

The study's most expensive discovery: Zephyr ships `st,stm32-digi-temp`, whose
name is exactly the peripheral the STM32N657 has, written for a different IP
block whose registers do not exist on this part. A devicetree node using it
compiles. `get_binding` describes it accurately and cannot say it will not work.

The session established this by grepping the SoC's CMSIS header for the register
macros the driver references and finding them absent — roughly a dozen shell
calls.

**Change, in order of cost.** `get_binding` and `search_bindings` should report
**which SoC series and boards upstream actually instantiates a compatible on**,
from the devicetree corpus already indexed. "Used by 6 boards, all
`stm32f4x`/`stm32l4x`, none on `stm32n6x`" is a cheap query against existing data
and would have redirected the session in one call. It does not prove
incompatibility; it is the strongest available signal, and it is currently
unavailable.

### T4 — Twister metadata is rendered as if it were the memory budget

`get_board` reports "1024 KB flash, 1024 KB RAM" for this board. The application
gets **511 KB** of SRAM and there is **no internal flash at all**. The figures
come from `twister.yaml` and are correct as metadata.

**Change.** Label them as Twister metadata where they are rendered, and where the
board's `_defconfig` sets `CONFIG_XIP=n`, say that the flash figure does not
describe an internal part. The data to do this is already indexed.

### T5 — `check_config` is the highest-value tool and was never used

It takes a whole file and returns a per-line verdict, making the same claims as
the write hook. It would have caught H1's promptless assignment had the guard
allowed it. Across three studies it has never been called once.

**Change.** This is a discoverability problem, not a capability problem. The
`announce-zephyr-write` hook already names it. Treat T5 as resolved by A1 rather
than by editing the tool.

## Skills

All eight must read as board-agnostic. The STM32N6 details stay only where they
are the evidence for a general rule.

### T6 — name the overlay and `.conf` filenames each build target actually matches

A board overlay whose filename does not match the **qualified** target is ignored
in silence. `app/boards/nucleo_n657x0_q.overlay` does not apply to
`nucleo_n657x0_q/stm32n657xx/sb`; the build fails much later with undefined
devicetree symbols — `__device_dts_ord_DT_N_ALIAS_die_temp_ORD undeclared` — which
reads as a code error. Nothing reports a missing overlay. The only positive
signal is `Found devicetree overlay:` in the configure output.

Zephyr builds the candidate names in `zephyr_build_string`
(`cmake/modules/extensions.cmake`), splitting `BOARD_QUALIFIERS` on `/` and
joining board and segments with `_`, which is why upstream's own file is
`tests/drivers/flash/common/boards/stm32n6570_dk_stm32n657xx_sb.conf`.

**This is the cheapest high-value tool change in the plan.** `get_board` already
enumerates every qualified target. It should render, per target, the exact
filenames that target will pick up:

```
nucleo_n657x0_q/stm32n657xx/sb
  overlay:  boards/nucleo_n657x0_q_stm32n657xx_sb.overlay
  conf:     boards/nucleo_n657x0_q_stm32n657xx_sb.conf
```

A developer adding a build variant is exactly the person who gets this wrong, and
they are already calling `get_board` to find the variant's name. Pair it with S9.

### T7 — `ZEPHYR_AI_INDEX` is the only way to steer index resolution, and nothing says so

`.mcp.json` sets `ZEPHYR_AI_PROJECT_ROOT` from `${CLAUDE_PROJECT_DIR}`, which the
CLI always sets to the session's own working directory. Exporting
`ZEPHYR_AI_PROJECT_ROOT` before launching a session therefore has no effect, and
the plugin silently resolves no index. Instrument 1's first run was voided by
exactly this: both plugin arms reported *"No project-specific Zephyr index is
available"* and one fell back to 62 web fetches.

The behaviour is correct — a session's project is its working directory — but it
is undiscoverable, and anyone driving the plugin from a script or a harness will
hit it.

**Change.** Name `ZEPHYR_AI_INDEX` as the override in the `index_status` output
and in the no-index message that `zephyr-index` already produces, alongside the
existing advice to build one. One clause: *"or set `ZEPHYR_AI_INDEX` to an
existing compatible index — `ZEPHYR_AI_PROJECT_ROOT` is overwritten by the
session's working directory and cannot be used for this."*

### S1 — verify the register contract, not the family name

**New content, `zephyr-drivers-sensors` and `zephyr-devicetree`.** A `compatible`
existing in-tree says nothing about whether it fits your silicon. Vendors reuse
peripheral *names* across incompatible implementations far more often than they
reuse implementations. Before adopting a driver on a new SoC in the same family,
check that the registers it references exist on your part, and check which SoCs
upstream actually instantiates it on.

Pairs with T3, which makes the check one tool call instead of a dozen greps.

### S2 — diagnosing a peripheral that will not enumerate

**New skill, or a major section of `zephyr-debugging`.** Two rules, both general:

- **The polled-succeeds / reply-fails signature.** A controller shifting bits out
  cannot tell whether anything is listening, so command-only phases "succeed"
  against dead silence, and the first operation needing a reply is where failure
  becomes visible. Read that asymmetry as a link-layer problem — clocking, signal
  integrity, pin configuration, power — not as a driver state machine. The first
  error you see is usually not the first thing that went wrong.
- **When a bus device will not enumerate, divide the clock before starting
  register archaeology.** A `max-frequency` property describes the data path the
  board designer cared about; probe, reset, and identification phases often run
  in a slower compatibility mode on the same divider. One line, reversible, high
  hit rate.

### S3 — a green build is not a runnable artifact

**`zephyr-build-flash`.** Post-link steps — sign, pad, encrypt, image-header,
partition-table, bootloader-concatenate — are where "build succeeded" and
"device boots" diverge, and several are warnings rather than errors when their
tool is missing. Verify the artifact, not the exit code:

```bash
which <post-link-tool>
ls -l build/zephyr/<expected-artifact>     # exists, and is newer than the elf
```

The STM32N6 signing path is the evidence: absent `STM32_SigningTool_CLI`, the
build is green, the binary is unsigned, and the board silently refuses it.

### S4 — when iteration is expensive, buy observability

**New skill.** When each cycle costs a human physical action — jumpers, power
cycles, cable swaps, a lab visit — the correct response is to shorten the loop,
not to think harder between iterations. Concretely: build a shell early; move
slow or failure-prone initialisation off the boot path so it happens at a moment
of your choosing with the console already up; bundle a confident fix, a candidate
fix, and better instrumentation into one image.

Include the counter-rule the session learned: know the framework's failure
semantics before offering an affordance. Zephyr's `device_init()` marks a device
initialised even when its init function fails, so a "retry" command that cannot
retry is worse than none.

### S5 — the bug class that actually bites is time and ordering

**`zephyr-rtos-patterns`.** Every defect the session introduced and found on
hardware was an assumption about *when*:

- statically-defined threads run before `main()`, so initialisation that assumes
  it runs first does not;
- boot is not instantaneous, so any liveness or timeout check evaluated during
  startup needs its baseline seeded rather than left at zero;
- **a configurable value's whole range must be checked against every timing
  constant it interacts with.** A 60 s configurable sampling interval against a
  3 s liveness window — each individually sensible — is a watchdog reset that
  neither module's code review would catch.

Add the fix pattern: decouple *how often the work happens* from *how often the
thread wakes*; slice long sleeps so a worker checks in regardless of duty cycle.

### S6 — watchdog details that turn a safety net into a brick

**`zephyr-rtos-patterns`.** Feeding a watchdog unconditionally proves only that
the feeding thread is alive; feed it conditionally on every worker having checked
in. And: an independent watchdog typically cannot be stopped once started and
survives a warm reset, so if boot ever exceeds the timeout, a warm reset produces
a boot loop that only a power cycle clears. Arm it before anything slow, or move
the slow thing off the boot path. Ask of any design: *what is the longest path
from reset to the first feed, including every failure mode with a timeout in it?*

### S7 — early-boot output is lossy, and garbled serial is a tooling smell

**`zephyr-debugging`.** Deferred logging drops what is emitted before the log
thread runs, which is exactly when drivers initialise; and a host-enumerated
transport is not connected for the first second or two regardless of firmware
configuration. The options are structural: synchronous logging for bring-up, move
the interesting work later, use a transport alive earlier, or replay diagnostics
on demand.

Corollary worth its own paragraph: **two readers on one serial port silently
split the byte stream**, and the result looks exactly like a device emitting
corruption. Check for competing readers before debugging firmware.

### S8 — boards whose debug port depends on strap state; and prerequisites triggering

**`stm32-platform`** gains the general form of the boot-pin lesson: on parts
where boot mode is selected by strap pins, the mode that runs the application and
the mode that exposes the debug port can be different, so "the probe cannot see
the core" is a configuration state and not a fault. Document the flash-then-run
cycle as a shape, not as one board's jumper numbers.

**`zephyr-prerequisites`** did not fire on a host that could not build. Its
description covers the symptom precisely; the trigger did not fire because
nothing in the session's phrasing matched it and the first build had not yet
failed. Add explicit trigger language for *before the first build in a new
workspace*, and have `zephyr-index` hand off to it after a successful index build
— indexing succeeding while building fails is the exact split the skill exists
for, and the moment the index completes is when it should be raised.

## Agents

### S9 — confirm a file was picked up; absence of an error is not evidence of use

**`zephyr-build-flash` and `zephyr-devicetree`.** Zephyr's file-selection
mechanisms — board overlays, board `.conf` fragments, shield files, suffixed
configs — match on constructed filenames and say nothing when a file matches
nothing. Adding a build variant is the moment this bites: the same file that
worked for the default target is silently ignored for the qualified one, and the
failure surfaces later as undefined devicetree symbols.

The general rule, which applies well beyond Zephyr: **when a build system selects
files by naming convention, confirm the file was consumed rather than inferring
it from the absence of a complaint.** Read the configure output for the positive
signal (`Found devicetree overlay:`, `Merged configuration`), and check it again
after changing the target rather than only after changing the file.

Pairs with T6, which turns "what should this file be called" into one tool call.

### A1 — no agent has fired in three studies, and the nudge is not the problem

Zero of four agents across ESP32/0.1.1, B-L475E/0.2.0 and this study. The reason
matters: the `announce-zephyr-write` PreToolUse hook **already names the
devicetree-specialist agent**, and it fired on ten config/devicetree writes here.
`check-build-failure` names the build-triage agent, and it fired on real build
failures. Both nudges landed and neither was taken.

So the hypothesis that agents fail to fire for want of a prompt is falsified.
Remaining hypotheses, in the order they should be tested:

1. **Cost.** A subagent that re-reads context the main loop already holds is a
   bad trade for a two-line overlay, and the model is right to decline. If so,
   the agents are scoped wrong: they should be reserved for work whose *breadth*
   exceeds one context, and their descriptions should say so.
2. **The description does not match the moment.** `devicetree-specialist` says
   "author or fix Zephyr devicetree"; the session's actual moment was "I have a
   binding that looks right and I need to know whether it fits this silicon."
3. **Handoff friction.** No agent can currently be given the session's working
   state, so it starts cold on a problem the main loop is warm on.

**Change.** Instrument before redesigning. Add to instrument 2's protocol an
explicit record of every moment an agent was named and declined, and treat A1 as
a measurement task for v0.8 rather than a change. Redesigning four agents on a
hypothesis nobody has tested is how the plural-lookup fix in 0.3.0 came to move
activation not at all.

### A2 — build-triage had opportunities and took none

Multiple real build failures occurred — a promptless assignment, an undeclared
identifier, a devicetree alias missing on an alternate board target. The hook
named the agent each time. The session diagnosed each itself, correctly and
quickly.

That is evidence the agent's threshold is wrong rather than its content: for a
one-line fix the main loop is faster, and honestly so. **Change:** narrow
`build-triage`'s stated trigger to failures that are genuinely non-local — a
build that fails differently between pristine and incremental, an error whose
first line names a file the developer did not write, a failure that persists
after the obvious fix — and stop naming it for single-symbol errors.

### A3 — the missing agent is hardware bring-up

The work that actually consumed this session has no agent: a peripheral that
will not enumerate, a flash that reads 779 times and fails the first write, an
alarming-but-irrelevant boot message, hypotheses to kill cheaply, and an
expensive iteration loop. That is a genuinely multi-context investigation with a
method — which is exactly what an agent is for, and the opposite of the two-line
overlay the current agents are named on.

**Change.** Add a `hardware-bringup` agent carrying S2, S4, S5, S6 and S7 as its
method: read the signature before the register map, divide the clock before the
archaeology, read the code behind an alarming message, prefer the hypothesis with
the cheapest disproof, extract counts from logs, and buy observability when the
loop is slow. Scope it to bring-up on real hardware, where breadth genuinely
exceeds one context.

## Method changes to the evaluation itself

Not plugin changes, but they gate the next study's validity.

**Hook rows must be resolved by replay, never from transcripts.** Session
transcripts record no hook output at all — the L475 session's 561 lines contain
zero occurrences of `hookSpecificOutput`, `additionalContext`, or `SessionStart`
though hooks ran throughout. Hooks are pure functions of payload and project
state; run them and read what they emit. This is how H1, H2 and H4 were
established, and each is exact rather than inferred.

**Count grounding acts, and split them by whether the index could answer.** The
headline 2.2% conflates a coverage gap with an activation gap. Splitting it —
45 lookups the index could answer, 27 it could not — is what turned one
uninterpretable number into M1 and A1.

**Record every moment an agent is named and declined.** Required by A1.
